# Supabase: criação do banco e histórico de migração

Este guia registra o cenário histórico de migração do projeto: sair do SQLite e usar PostgreSQL no Supabase, substituindo imagens Base64 por URLs públicas no Storage.

Os scripts avulsos de migração não fazem mais parte da árvore ativa do projeto. Para novas instalações, use o schema atual e configure o app diretamente com `DATABASE_URL` apontando para o Supabase.

## 1) Criar o projeto no Supabase

1. Acesse https://app.supabase.com e crie um novo projeto.
2. Anote o **Project URL** (ex: `https://xxxx.supabase.co`).
3. Em **Project Settings → API**, copie a **Service Role Key** (necessária para upload no Storage).

> **Importante:** a Service Role Key é sensível; use somente via variáveis de ambiente.

## 2) Criar o bucket público no Storage

Você pode criar pelo painel:
1. **Storage → Buckets → New Bucket**
2. Nome sugerido: `post-images`
3. Marque como **Public**

O script também tenta criar o bucket automaticamente se não existir, mas manter essa etapa explícita ajuda em produção.

## 3) Criar tabelas de usuário e post no PostgreSQL (Supabase)

Abaixo estão **as tabelas completas** de acordo com os modelos atuais do projeto (`models.py`).

### Tabela `user`

```sql
create table public."user" (
  id integer primary key generated by default as identity,
  username varchar(100) not null unique,
  password_hash varchar(128) not null
);
```

### Tabela `post`

```sql
create table public.post (
  id integer primary key generated by default as identity,
  title varchar(255) not null,
  content text not null,
  created_at timestamptz not null default now()
);
```

### Observações importantes
- O script faz `UPSERT` usando `id`, então **id precisa ser PRIMARY KEY**.
- O campo `content` recebe o HTML já com as URLs públicas das imagens (sem Base64).

## 4) Configurar variáveis de ambiente

Antes de rodar a migração, configure:

```bash
export SQLITE_PATH="instance/blog.db"
export PG_DSN="postgresql://user:pass@host:5432/postgres"
export SUPABASE_URL="https://xxxx.supabase.co"
export SUPABASE_SERVICE_KEY="service_role_key"
export SUPABASE_BUCKET="post-images"
```

Para que novos posts façam upload automático de imagens no Storage, o app também
precisa destas variáveis no ambiente de execução (mesmas chaves acima).

### Onde definir no servidor (recomendado)

Em produção, defina as variáveis no **serviço de hospedagem** (Render/Railway/Docker/PM2/Systemd),
e não no terminal interativo. Exemplos:

- **Systemd** (Linux):
  - Crie um arquivo `/etc/systemd/system/blog.service` com `Environment=...`
  - Ou use um arquivo de ambiente: `EnvironmentFile=/etc/blog.env`
- **Docker**:
  - Use `-e SUPABASE_URL=...` e `-e SUPABASE_SERVICE_KEY=...` ou `--env-file`
- **Panel/Cloud**:
  - Use o painel de variáveis de ambiente do provedor

### Windows (para uploads de imagem também)

Você precisa definir **DATABASE_URL**, **SUPABASE_URL** e **SUPABASE_SERVICE_KEY**
no Windows para que o app grave no Supabase e envie imagens para o Storage.

**PowerShell (sessão atual):**
```powershell
$env:DATABASE_URL="postgresql://postgres:SEU_PASSWORD@db.<projeto>.supabase.co:5432/postgres"
$env:SUPABASE_URL="https://<projeto>.supabase.co"
$env:SUPABASE_SERVICE_KEY="<service_role_key>"
$env:SUPABASE_BUCKET="post-images"
python run.py
```

**CMD (sessão atual):**
```cmd
set "DATABASE_URL=postgresql://postgres:SEU_PASSWORD@db.<projeto>.supabase.co:5432/postgres"
set "SUPABASE_URL=https://<projeto>.supabase.co"
set "SUPABASE_SERVICE_KEY=<service_role_key>"
set "SUPABASE_BUCKET=post-images"
python run.py
```

**Permanente no Windows:**
1. Painel de Controle → Sistema → Configurações avançadas do sistema
2. Variáveis de Ambiente → Variáveis do sistema
3. Adicione as variáveis acima
4. Reinicie o terminal/serviço

Opcional:

```bash
export BATCH_SIZE="100"
export UPLOAD_RETRIES="5"
export UPLOAD_BACKOFF_SECONDS="2"
export SKIP_EXISTING="true"
```

## 5) Migração histórica

O processo original:
- lê o SQLite em batches;
- extrai imagens Base64 do HTML;
- faz upload para o Storage;
- substitui o `src` por URLs públicas;
- grava no Postgres via UPSERT.

Usuários também foram migrados copiando `id`, `username` e `password_hash` do SQLite para o Postgres.

## 6) Pós-migração (boas práticas)

- Se aparecer erro de `duplicate key value` ao criar novos posts, ajuste a sequência do
  ID no Postgres para o maior valor migrado:

```sql
select setval(pg_get_serial_sequence('post', 'id'), (select max(id) from post));
select setval(pg_get_serial_sequence('user', 'id'), (select max(id) from "user"));
```

- Valide posts aleatórios (HTML + imagens).
- Após validar, remova imagens inline do legado ou descarte o SQLite antigo.
- Mantenha backups antes e depois do processo.

## 7) Migração 2026-08 — ON DELETE CASCADE (correções de segurança)

O app agora apaga comentários/respostas/tags junto com o post via `ON DELETE
CASCADE`. As FKs criadas antes não têm CASCADE — aplique no SQL Editor do
Supabase. **Não apaga nenhum dado existente** (só altera a definição das FKs).

**Passo 1 — confirme os nomes das constraints:**
```sql
select conname, pg_get_constraintdef(oid)
from pg_constraint
where conrelid in ('public.comment'::regclass, 'public.post_tags'::regclass)
  and contype = 'f';
```

**Passo 2 — aplique (ajuste os nomes se o passo 1 mostrar diferente):**

> **Observação verificada em produção (2026-08-15):** as FKs de `comment`
> (`comment_post_id_fkey`, `comment_parent_id_fkey`) **já vinham com CASCADE**
> no banco existente — só `post_tags` precisou de migração. Confirme pelo
> passo 1: se a constraint já aparece com `ON DELETE CASCADE`, **pule o
> ALTER correspondente** (evita lock desnecessário). Os 4 ALTERs abaixo são
> seguros de rodar por completo (drop + add é idempotente), apenas redundantes
> para as FKs que já têm CASCADE.

```sql
-- Só rode os ALTERs das FKs que ainda NÃO têm ON DELETE CASCADE (passo 1).
alter table public.comment drop constraint comment_post_id_fkey;
alter table public.comment add constraint comment_post_id_fkey
  foreign key (post_id) references public.post(id) on delete cascade;

alter table public.comment drop constraint comment_parent_id_fkey;
alter table public.comment add constraint comment_parent_id_fkey
  foreign key (parent_id) references public.comment(id) on delete cascade;

alter table public.post_tags drop constraint post_tags_post_id_fkey;
alter table public.post_tags add constraint post_tags_post_id_fkey
  foreign key (post_id) references public.post(id) on delete cascade;

alter table public.post_tags drop constraint post_tags_tag_id_fkey;
alter table public.post_tags add constraint post_tags_tag_id_fkey
  foreign key (tag_id) references public.tag(id) on delete cascade;
```

**Teste (opcional, em um post descartável):** exclua um post que tenha comentários
e confirme que os comentários somem junto.
